# Porting a `checks/*.sh` script to a Rust document check

The ticket checks under `checks/` are bash wrappers around embedded Python,
one per ticket. They move into this crate one at a time:
- the document assertions become `cargo test` tests on the library
  `hadronyche_tools::doccheck`;
- the assertions that run tools or read repository state go to
  `scripts/repo-state.d/<id>.sh`;
- the script is deleted in the same commit.

This file is the procedure. It is written so that several porters can work in
parallel without editing the same files.

## Rulings that bind every port

1. **Equivalence first.** A port reproduces *its own script's* variant of
   every rule, even where scripts disagree. The same rule is written about
   fifteen ways across the scripts (`swarm/notes/checks-inventory-2026-11-16.md`,
   section 4).
   - The library offers each disputed rule as a function that takes an
     explicit, named policy. The port names its script's policy at the call
     site.
   - Unifying the variants is a later, separate, reviewed step. It is never a
     side effect of a port.
2. **The repertoire guard (R13), by construction (R20).** A check whose
   input holds a character outside the repertoire fails with its own
   criterion `REPERTOIRE` (file:line:column and the code point) and
   nothing else.
   - The guard is a property of `Docs`, not a list a port keeps. A check
     runs only through `CheckSpec::evaluate`, which hands it a logged view
     of the documents: every text it obtains from `Docs::read` (wire.md, a
     ticket, a separate review record, a link target outside `doc/` such as
     `../../../README.md`) is guarded after the run. One character outside
     the repertoire in any text the check read makes the verdict
     `REPERTOIRE` alone, one failure per such file. A port calls no guard.
   - The repertoire is `data/repertoire.tsv`. It holds ASCII printable,
     `\t`, `\n`, `\r`, and the 44 other characters of `doc/`:
     § ± ² ³ µ · ¹ × ÷ Δ Σ α π τ – — ‖ … ‰ ⁴ ⁵ ⁶ ⁹ ⁻ ₁ ₂ ₃ ⅓ ⅔ → ↔ ⇒ ∈ − ∞ ≈
     ≠ ≡ ≤ ≥ ⌈ ⌉ ⌊ ⌋.
   - `\r` is allowed because every script read with `open()`, so `\r`
     reached the script as `\n`.
   - Each character comes with its Python facts (`\w`, `\d`, `\s`, the
     `splitlines` boundary, `re.I` partners, `lower`, `upper`, NFKC),
     generated by `tools/gen_repertoire.py` with Python 3.10 and 3.13,
     which agree. `casefold` is not recorded: no port uses it, and a
     column no test proves is not kept.
   - `repertoire::tests` proves, without running Python, that for every
     character the library's `\w`, `\d`, `\s`, `\b`, `\B`, `strip`,
     `splitlines`, `re.I` folding and `lower`/`upper` equal the table.
   - Inside the repertoire the port must equal its script. Outside it the
     port is red by rule, and the harness itself classifies the row "port
     stricter (outside repertoire)". A denial that brings in such a
     character expects `REPERTOIRE`.
   - **Adding a character** (the `REPERTOIRE` message says the same):
     commit the document that holds it, then, from the repository root,

     ```
     python3 hadronyche-tools/tools/gen_repertoire.py > hadronyche-tools/data/repertoire.tsv
     cargo test -p hadronyche-tools repertoire
     ```

     The generator takes `python3.10` and `python3.13` from `PATH`, or
     `--python PATH` once per interpreter; `--commit C` reads another
     commit (default `HEAD`). `--check hadronyche-tools/data/repertoire.tsv`
     compares the rows instead of printing them, with whichever
     interpreters are available. The row count is derived, not pinned; a
     test checks that every character of `doc/` in the working tree has a
     row. The tests then force the proof for the new row. Never widen the
     guard in a port.
3. **Python compatibility is part of equivalence (R1).** Inside the
   repertoire, wherever the script's Python differs from Rust's defaults,
   use `doccheck::pycompat`, never the Rust default:
   - Send every pattern through `text::rx`. It gives Python's `\w`, `\W`,
     `\s`, `\S`, `\b`, `\B` and `$`: `²` is a word character; `\b`/`\B`
     run as `fancy-regex` look-arounds over Python's class, with a
     plain-regex prefilter; `$` without `(?m)` also matches before a
     trailing newline. Iteration, `replace*` and `split` follow Python
     3.7's empty-match rule (`re.sub("x*", "-", "abxd")` is `-a-b--d-`).
     A port never uses `text::rx_raw` (the source test forbids it).
   - **Look-ahead and look-behind are supported.** Copy the script's
     pattern as written: `(?<![\w.\-])(\d+)(?![\w]|\.\d)`, `(?<!not\s)`,
     `re.split(r"(?<=[.;])\s+", …)`. They run on `fancy-regex` over
     Python's classes, with a plain prefilter that drops them; the
     scripts' own look-around patterns are proven equal to Python's `re`
     (search, groups, `finditer`, `split`, `sub`) on
     `data/pycompat_corpus.txt`. Never emulate a look-behind by hand: the
     private emulations in the packages differed from Python (see
     MIGRATING-PACKAGES.md).
   - **Regex constructs not supported: the port fails to build its
     pattern.** `\Z`, `{,n}` and back-references (`\1`, `(?P=name)`) are
     refused (`pycompat::unsupported`); no script uses them. A refused or
     non-compiling pattern never panics: a literal one fails the library
     test `source_rules::every_literal_pattern_builds`; at check time it
     turns the check red under `REGEX_LIMIT`. Rewrite the pattern (`\z`
     for `\Z`, `{0,n}`, a capture compared in code).
   - **A regex engine failure is red, never "no match" (R19).** Python has
     no backtracking limit; `fancy-regex` stops at `rx::BACKTRACK_LIMIT`
     steps. `Rx` records any engine failure (that limit, a refused
     pattern) on the thread, and `CheckSpec::evaluate`, the only caller of
     a check's `run`, turns the verdict red under `REGEX_LIMIT` alone,
     with the pattern and the file:line of the text being matched. A check
     cannot see, clear or ignore the record: the source tests forbid
     `take_failures`, `restore_failures`, `.evaluate(` and any call of
     `run` other than `evaluate`'s. A denial whose input makes the port hit
     the limit expects `REGEX_LIMIT`.
   - **An integer beyond `i128` is red, never wrapped (`INT_LIMIT`).**
     Python's `int` is unbounded. `pycompat::parse_int` (and
     `text::first_int`/`ints`), `PyValue::py_int` on a TOML big integer,
     `pynum::eval_arith` and `pynum::Fraction::from_f64` record any value
     beyond `i128` on the thread; `CheckSpec::evaluate` turns the verdict
     red under `INT_LIMIT` alone, located where the number is written,
     and the harness classifies it `IntLimit` (port stricter). The source
     tests forbid `take_int_limits`/`restore_int_limits` outside the
     library. Never saturate, wrap or carry a private big-integer type.
   - **Python numbers** come from `pynum`, proven on the corpus:
     `py_float` (`float()`), `str_float`/`format_float(x, spec)` (`repr`,
     `str`, `f"{x:g}"`, `:.2f`, `:+.3f`, `:.3e`), `percent_float`
     (`"%.4g" % x`, `%d`, `%s`), `eval_arith` (`eval` over `+ - * **`,
     with Python's precedence, literal rule and int/float result,
     `PyNum`, `EvalError`), `Fraction` (`Fraction(a, b)`, `Fraction(x)`,
     `limit_denominator`, `str`).
   - Character-indexed slicing with negative indices:
     `pycompat::py_slice(s, start, stop)`. Truthiness: `PyValue::truthy`.
     NFKC: `pycompat::nfkc` (inside the repertoire; proven per row and on
     the corpus).
   - For `strip`, `lstrip`, `rstrip` and `split()`, use the `PyStr` trait.
     Never use `trim` or `split_whitespace` in a check.
   - Read with universal newlines, then split as the script did:
     `LineSplit::Nl` (`split("\n")`) or `LineSplit::PySplitlines`.
   - Paths: `docs::join` is `os.path.normpath`. A leading `..` is kept, and
     a path outside the repository names no document.
   - Send every digit capture through `pycompat::parse_int` (or
     `text::first_int`/`ints`). They are checked: a number beyond `i128` is
     reported. A check contains no `.parse` and no `unwrap_or(0)`; a source
     test fails otherwise.
   - Read TOML values through `PyValue`: `py_int`, `is_int`, `eq_int`,
     `py_eq`, `py_iter_str`, `py_dicts`, `py_str`.
4. **TOML by construction (R14).** A port reads `wire.toml` through a
   faithful port of ITS script's reader, named by `TomlReader`:
   - `Subset004_18`: the statement-scanner subset reader of 004-03 (a
     variant), 06, 08-13, 16-20 and 24-29.
     - It lives in `doccheck::tomlsubset`, ported line for line.
     - It is proven equal to the Python original on the 95-snippet corpus
       `data/toml_corpus.txt` (`tools/gen_toml_corpus.py`).
     - Like the script, it rejects triple-quoted strings (double or single
       quotes) and accepts a leading-zero `040`, duplicate keys, a bare
       `C-116` and big ints, so there is no difference to excuse.
   - `Tomllib`: 004-22 only. It uses the crate's parser into `PyValue`
     (`doccheck::tomllib`). Its differences from `tomllib` on the corpus
     are listed in `tomllib::KNOWN_DIFFERENCES`: two, both ints beyond 64
     bits.
   - `Line004_14` / `Line004_15`: the line readers of 004-14 and 004-15
     (`doccheck::tomlline`, `Variant::V004_14` / `V004_15`), ported from
     the scripts. They return `Doc { messages, others }`: each
     `[[message]]` dict starts as `{"name": None, "fields": []}`, and the
     other tables are by name, a dict for `[x]` or a list of dicts for
     `[[x]]`. A scalar is `true`/`false`, else `int(t, 0)`, else
     `int(t, 10)` (`040` is 40), else the text as written. An array is
     every string or integer token on the line (`[1.5]` is `[1, 5]`). The
     two copies differ: 004-15 keeps strings as written, raises
     `IndexError` for a field before any message, and crashes
     (`AttributeError`) on `[[x]]` after `[x]`. `Error::caught_by(variant)`
     says whether the script printed `FAIL setup` or crashed.
   - The corpus generator `tools/gen_toml_corpus.py` runs EVERY script's
     copy of a reader (20 copies of `Subset004_18`; both line readers) on
     Python 3.10 and 3.13, taking `python3.10` and `python3.13` from `PATH`
     or `--py310`/`--py313`. It fails unless the interpreters agree and all
     copies of one variant agree. A script whose copy differs gets a new
     named variant. Never port a reader from another port's private copy:
     the four packages' copies all disagreed with Python on the corpus
     (`MIGRATING-PACKAGES.md`).
   - Python's `int()` refuses a decimal string of more than 4 300 digits.
     The readers reproduce it: the subset and line readers keep such a
     scalar as a string, and the line readers' array token raises
     `ValueError`.
   - Not ported (no package needs them yet): 004-21's `json.loads` line
     reader and 004-04's `toml_blocks`. Each is a distinct reader and gets
     its own variant when its script is ported.

   When the script's reader, or its use of the values, raised an exception
   the script did not catch (KeyError, TypeError, `tomllib` errors), the
   port calls `Report::crash(why)`. A crash is its own outcome, which the
   harness matches to the script's traceback. When the script caught the
   exception (the subset reader's errors in 004-27), the port reports the
   script's criteria.

   **One `Stop` type.** A check body that may stop early returns
   `Flow<T>` (`Result<T, Stop>`) and propagates with `?`;
   `Report::finish(flow)` applies it. `Stop::Crash(why)` is an uncaught
   exception (it becomes `Report::crash`); `Stop::Exit { criterion,
   message, earlier }` is `print("FAIL …")` then `sys.exit(1)`, keeping the
   failures already printed (`Earlier::Kept`) or dropping the ones the
   script collected for a final print it never reached
   (`Earlier::Dropped`, 004-14). Never model a crash as a failure with
   criterion `"CRASH"` or as a FAIL under another criterion: the harness
   matches only `Report::crash` to the script's traceback.
5. **Not ported.** These stay scripts, and the suite keeps running them:
   - 003-01, 003-03, 003-04, 003-06, 003-07, 003-09: they freeze-check,
     build or run the proof of concept;
   - 003-02, 003-05, 003-08: their content parts read files outside the
     repository (untracked notes, the proof of concept's `BASELINE.md`).
6. **Tool gates run once.** An assertion that runs a tool would be circular
   or environment-dependent inside `cargo test`. Examples: `cargo run --bin
   wire-check`, `cargo test --test wire_tables`, `check-design.py`, sibling
   scripts, git against a ref, the proof of concept.
   - Such assertions go to `scripts/repo-state.d/<id>.sh`.
   - `scripts/repo-state-checks.sh` runs each tool once, with the scripts'
     900 s timeout, and exposes the results.
   - Per-ticket pins ("at least 12 passed") stay as named lines.
7. **A check reads only its `Docs`, and no port imports another (R16).**
   - Clippy enforces it. `hadronyche-tools/clippy.toml` bans, in the whole
     crate: `std::fs`, `std::process`, every function of `std::env`
     (`args_os`, `vars_os`, `set_var` included), `Path::exists`/`is_file`,
     `Docs::repo`, `Docs::dir`, `Docs::at_commit`, `repo_root` and
     `commit_exists`.
   - The only `#![allow(clippy::disallowed_methods,
     clippy::disallowed_types)]` are in:
     - `doccheck/docs.rs`, `doccheck/testing.rs` and `doccheck/equiv/`;
     - the crate's other tools (`wire_tables.rs`, `metrics_check.rs`,
       `src/bin/`, `build.rs`) and their own test files.
   - A source test (`testing::source_rules`) covers what clippy cannot see.
     In check modules and `tests/doc_*.rs` it forbids:
     - `include!`, `include_str!`, `include_bytes!` and `#[path]`;
     - any opt-out of the clippy rule;
     - in a check module, matched on whitespace-stripped code: `.parse(`,
       `parse::<` (`str::parse::<u32>`, `.parse :: <usize>()`),
       `from_str(`, `unwrap_or(0)` (`unwrap_or( 0 )`), `.evaluate(`; and the
       words `testing` (an aliased `use … testing as t` too) and `rx_raw`;
     - everywhere: `run)(`, `take_failures`, `restore_failures` (R19);
     - in a check module (review round 4): `thread::`, a `static` item,
       `OnceLock`, `LazyLock`, `OnceCell`, `thread_local!`, `Mutex`,
       `RwLock` and atomics. A check runs on the evaluating thread and
       keeps no state across evaluations; otherwise a regex failure on
       another thread, or a result cached from an earlier evaluation,
       would escape `REGEX_LIMIT`. Clippy also bans thread spawning, and
       `Docs::overrides`, `export` and `source` (text handed out without
       being logged) outside the harness;
     - a path to another port with any prefix (`checks::c<id>::`,
       `super::c<id>::`, `super::super::c<id>::`): NO PORT IMPORTS ANOTHER
       PORT.
   - Shared code belongs in the library: `doccheck::family004` holds the
     004 family's field-table helpers. `build.rs` refuses any entry under
     `checks/` that is not a port.
   - Test files get documents only from `doccheck::testing`: `report_of`,
     `red_phase` and `check_denial`.
8. **Header and code disagree → follow the code.** The code is what has been
   passing. Record the disagreement in the test's doc comment.
9. **A check reports, never panics,** on any input.
   `checks::tests::no_check_panics_on_malformed_input` and
   `no_check_panics_on_real_documents_with_one_corruption` run every
   registered check on malformed documents.
10. **`claims` is for new checks only (R15).** A port reproduces its
    script's own regex exactly and never uses `must_affirm`/`claims`.
    Those helpers are keyword detectors; their module documentation lists
    the guard forms they handle and the known limits.

## What a port consists of

For ticket `<id>` (`004-27`), with `<mod>` = `c` + the id with `-` as `_`
(`c004_27`):

| File | What |
|---|---|
| `src/doccheck/checks/<mod>/mod.rs` | the check: `pub fn run(docs: &Docs) -> Report`, `pub const SPEC: CheckSpec`, `const KNOWN` (classified differences); split into files per criterion |
| `src/doccheck/checks/<mod>/denials.rs` | `pub const DENIALS: &[Denial]`: the denial list (see below) |
| `tests/doc_<id>.rs` | one `#[test]` per acceptance criterion and DoD item, the red-phase test, and `hadronyche_tools::denial_tests!(SPEC; …)` with every denial name |
| `equivalence/<id>.md` | the committed harness summary |
| `scripts/repo-state.d/<id>.sh` | the relocated repository-state assertions |
| `checks/<id>.sh` | deleted, in the port's commit |

There is no registry to edit: `build.rs` generates it from
`src/doccheck/checks/c<digits>…`. A malformed entry fails the build with a
message, for example a directory without `mod.rs` or a `c…` file that is not
`.rs`.

`SPEC` fields:

| Field | What it holds |
|---|---|
| `id` | the ticket id |
| `run` | the check function |
| `script_env` | the override variables that make the script skip its cargo runs, usually `[("WIRE_MD", "doc/design/spec/wire.md")]` |
| `targets` | the sections the corpus mutates |
| `keywords` | extra words to negate |
| `known_differences` | `KNOWN` |
| `denials` | `denials::DENIALS` |
| `toml` | the script's `TomlReader` |

## Which files a porter may edit

- **Yours alone:**
  - `src/doccheck/checks/<mod>/` (all of it);
  - `tests/doc_<id>.rs`;
  - `equivalence/<id>.md`;
  - `scripts/repo-state.d/<id>.sh`;
  - deleting `checks/<id>.sh`.
- **Shared, by addition only:** a new shared tool goes in
  `scripts/repo-state-checks.sh`, as one block in "shared tool runs" that
  exports its results. On a merge conflict, keep both blocks.
- **Not yours:**
  - every other file of `src/doccheck/` (the library and the harness);
  - other ports;
  - `scripts/per-change-suite.sh`;
  - `.github/`;
  - anything under `doc/`;
  - every other script under `checks/`. Never weaken or edit one; the only
    allowed change to a script is deleting your own, with its port.

### Adding to the library, and fixing a library bug

The library is shared by every port, so a change to it can break another
port's equivalence.

1. **Start private.** Write a helper in your own module
   (`src/doccheck/checks/<mod>/helpers.rs`). Your port lands with it.
2. **A new rule variant** is a new named policy: a new enum variant or a new
   constant (`TagPolicy::PROSE_004_25`, `TableRules::…`), documented in its
   module's table with the scripts that use it. Never change what an
   existing policy does: other ports were proven with it.
3. **A library addition** is its own commit or PR touching only
   `src/doccheck/` (`feat(tools): doccheck <what>`). It carries unit tests
   and adds only.
4. **A library bug fix** changes existing behaviour, for example a Python
   semantic the library got wrong (round 1 of PR #42 fixed `\w`,
   `normpath`, `splitlines`, the separator rule). It goes in a library PR
   that:
   - fixes the primitive and adds a unit test for it;
   - reruns `cargo run --release -p hadronyche-tools --bin doccheck-equiv --
     --all --out hadronyche-tools/equivalence`, which reruns every
     registered port with its denials;
   - commits the regenerated summaries;
   - lists in the PR every port whose summary changed and why.

   A port that becomes "port weaker" blocks the fix until it is resolved.
5. After an addition merges, switch your port to it in a follow-up and rerun
   the harness for your id.

## The denial list

A denial is the real documents with one edit applied in memory, plus what
the port must report on them (`Denial { name, file, edit, expect }`):
- `edit` is a `DenialEdit::Text(fn)` built from `doccheck::mutate` helpers,
  or `DenialEdit::Delete`;
- `expect` lists `(criterion, message substring)` pairs (`""` matches any
  message):
  - the port's failed criteria must EQUAL the criteria listed;
  - an empty `expect` means the port passes;
  - `("CRASH", "")` means the port models the script's crash.

  The criteria are the old script's verdict on the same documents (the
  reference), `REPERTOIRE` when the edit brings in a character outside
  the repertoire, or `REGEX_LIMIT` when it makes the port's regex engine
  fail (R19).
- `mutate::anchored_replace(text, anchor, old, new)` is the review's edit
  form: it finds the anchor and replaces the first `old` at or after it;
  `old = "ALL\n"` replaces every newline.

Every port has ONE list (`denials.rs`), used twice:
- **as tests:** `denial_tests!(SPEC; name, …; slow: name, …)` makes one
  `#[test]` each, plus a test that the list and the tests agree. Every
  denial that expects `REGEX_LIMIT` (a backtracking input: seconds per test
  in a debug build) must be listed after `slow:`; those are `#[ignore]`d in
  the default `cargo test` and run in release by CI's "Slow denials" step
  and the per-change suite (`cargo test --release -p hadronyche-tools
  --test 'doc_*' -- --ignored`, under a second each);
- **by the harness against the old script:** the targeted denials are the
  strongest evidence, since a random corpus is only 8–13 % red.

Write one denial per negative the script's header lists, plus one per
assertion that has none. Scope an edit with `mutate::within_section` when
the same words occur in an earlier section.

## Procedure

1. **Read the script whole**, header and code.
   - Number every assertion it makes (every `fail`, `check` or `bad` call).
   - Mark each one as *document* (reads files under `doc/`) or *repository
     state* (runs a tool, reads git or the proof of concept, greps its own
     text).
   - Note where its Python semantics matter: how it reads and splits
     lines, `\w`, `int()`, TOML values.
   - Note where the header and the code disagree.
2. **Name the variants.** For every shared rule the script uses, find or add
   the policy that reproduces it exactly.
3. **Write the check** in `src/doccheck/checks/<mod>/`.
   - Keep the script's criterion labels (`AC1`, `DoD`, `WIRE`) as the
     `Report` criteria; the harness compares them criterion by criterion.
   - Keep each function under 100 code lines (`scripts/function-length.py`).
4. **Write the denial list and the tests**, then fill `SPEC`.
5. **Run the harness** (below) until it says EQUIVALENT. Classify every
   difference that is genuinely not "port weaker" in `KNOWN`, with a reason
   a reviewer can check.
6. **Relocate** the repository-state assertions to
   `scripts/repo-state.d/<id>.sh`, and run `bash
   scripts/repo-state-checks.sh`.
7. **Commit** with the Conventional Commits title `test(<id>): port
   checks/<id>.sh to Rust; delete the script`. The commit holds the check,
   the denial list, the test file, `equivalence/<id>.md`, the repo-state
   file, and `git rm checks/<id>.sh`.
   - The message lists every assertion of the script and where it now
     lives.
   - Nothing a script asserted may disappear. An INFO or NOTE print is not
     an assertion.

### Gates before a port is pushed

- `cargo test --workspace`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo fmt --check`
- `python3 scripts/function-length.py`
- `python3 doc/kickoff/check-design.py doc/design`
- `bash scripts/repo-state-checks.sh`
- every remaining `checks/*.sh` still green
- the harness summary EQUIVALENT

## The harness

`doccheck-equiv` lives in `src/doccheck/equiv/`, with the bin
`src/bin/doccheck-equiv.rs`. Usage:

```
cargo run --release -p hadronyche-tools --bin doccheck-equiv -- <id> --out hadronyche-tools/equivalence/<id>.md
cargo run --release -p hadronyche-tools --bin doccheck-equiv -- --all --out hadronyche-tools/equivalence
cargo run --release -p hadronyche-tools --bin doccheck-equiv -- <id> --denials-only     # quick: (a) and the denials
```

**The committed run is the default.** It covers:
- **(a)** the current tree: both must pass;
- **(b)** the tree at the commit that first added the script: both red on
  the same criteria;
- **(c)** four seeds (2026, 7, 31337 and 99) of 2 000 structured mutations each: rows,
  units and subsections deleted, tags stripped, keywords negated, numbers
  incremented, headings renamed. Each (kind, target) group is shuffled by
  the seed, then targets and kinds take turns;
- **(d)** the denial list, on both the script and the port.

Other options: `--seeds A,B`, `--limit N`, `--no-red`, `--no-denials`,
`--jobs N` (sandboxes in parallel, default 4), `--script-timeout S`
(seconds per script run, default 60), `--full` (every row; never
commit it). `--all --out DIR` creates DIR.

It writes the **summary**: the tree and script commits, counts per seed and
for the denials, rows (a) and (b), and every row that is not "same". A
script run takes about 0.3 s; with four sandboxes the committed run takes
about 30 minutes per check on a quiet machine.

**Comparison.**
- "Same" means both pass, or both fail the same set of criteria.
- Every other pair is a difference of a kind:
  - script red, port pass;
  - script pass, port red;
  - port fails more criteria;
  - port misses a criterion;
  - script crash with port red;
  - script crash with port pass;
  - script timed out with port red;
  - script timed out with port pass.
- A script **crash** is its own outcome. It is one of: the interpreter's
  traceback (a line `Traceback (most recent call last):` at column 0
  after the last FAIL, PASS, OK or NOTE line; a FAIL message that quotes
  the words is not one), or a non-zero exit with no FAIL line. It matches
  only a port that models the crash (`Report::crash`), never a port red.
- A script still running at the per-script timeout (`--script-timeout`,
  60 s) is **timed out**, its own outcome: a backtracking pattern takes
  Python minutes (242 s for one review row), which must not stall a
  corpus. It is never "same".
- FAIL labels may be written `AC1`, `AC 1` or `AC-1`; they are normalised.
  The reader also takes `FAIL AC2 (note):`, `FAIL [AC1] …`, extra spaces,
  an indented `FAIL`, and grouped results under a header such as `  AC1`,
  `  DoD` or `  WIRE`. Any other `FAIL <text>` line is the pseudo-criterion
  `UNREADABLE`: reported, never "same", never a crash. A traceback is the
  header `Traceback (most recent call last):` at column 0 followed by a
  `  File` frame; a quoted header is not one.
- A summary (`--out`) is refused from a tree with uncommitted changes to
  tracked files other than `hadronyche-tools/equivalence/` (the summaries
  themselves); `--allow-dirty` names them in the header instead. The tree
  is recorded when the run starts.
- A script that prints FAIL and exits 0 counts as red and is reported as an
  anomaly; in (a) or (b) it fails the run.
- A port red on `REPERTOIRE` is classified "outside repertoire" by the
  harness itself, whatever the script says.
- A port red on `REGEX_LIMIT` is classified "port stricter (regex limit)"
  by the harness itself when the script is red, timed out, crashed or
  passed: the port is red, so it is never weaker. A script that timed out
  against a port that passes, or against an ordinary port red, is
  unclassified.
- Every edit of the export is read back after writing and after restoring.
  Any error aborts the run, so an unapplied mutation can never read "same".

**Acceptance rule.**
- A difference passes only when a `KNOWN` entry matches its label, with a
  class allowed to excuse that kind:

  | Class | Use |
  |---|---|
  | `OutsideRepertoire` | applied by the harness itself (never listed): the port is red on `REPERTOIRE` |
  | `RegexLimit` | applied by the harness itself (never listed): the port is red on `REGEX_LIMIT` (R19) |
  | `IntLimit` | applied by the harness itself (never listed): the port is red on `INT_LIMIT` |
  | `PortStricter` | the port rejects what the script accepted, for a stated reason |
  | `PortStricterTyped` | a typed reader rejects what Python let through (now rare: the readers are faithful) |
  | `ScriptWrong` | the script's verdict is wrong; the reason says how |
  | `SubsetTomlReader` | kept for a reader not yet ported faithfully; unused by the pilots |
  | `ScriptCrashed` | the script crashed where the port cannot model it; prefer `Report::crash` |

- The weaker kinds are "**port weaker**": script red with port pass, port
  missing a criterion, script crash or timeout with port pass. No class
  excuses them, except `SubsetTomlReader`, and `RegexLimit` for a port
  missing the script's criterion because it reports `REGEX_LIMIT` alone.
- The pilots list no `KNOWN` entry at all: with the repertoire guard, the
  faithful readers and the modelled crashes, every row is "same",
  "outside repertoire" or "regex limit".
- An unexcused difference, or a denial whose expectations the port does
  not meet, fails the run.

**How the script runs.**
- The harness exports `doc/` from the same `Docs` the port reads (the
  working tree, or `git archive` of the red-phase commit) into a temporary
  directory outside the repository, about 14 MB, removed on exit.
- It writes the script to `checks/<id>.sh` there and runs it from that
  directory, so fixed paths resolve inside the export.
- `script_env` points override variables at the exported files.
- A `cargo` stub that exits 97 makes any un-skipped cargo run red.
- A deleted script is read from the parent of the commit that deleted it.

**Limits.**
- Only `doc/` is exported, so a script that reads outside it cannot be
  compared (one reason for the not-ported list).
- The corpus is structural and mostly neutral; that is why there are
  denials.
- Mutations are line-based and never touch fenced code.

**Where it runs.** Never in `cargo test`, the per-change suite or CI. It
needs the old scripts and Python.

## Red-phase tests

```rust
#[test]
fn red_phase_tree_fails_every_criterion() {
    red_phase(&SPEC, "<full commit>", &["AC1", "AC2", "AC3", "AC4", "DoD"]);
}
```

- A missing commit **fails** the test. With `DOCCHECK_ALLOW_SHALLOW=1` it
  prints a visible `SKIPPED` line instead.
- A run prints a visible `EXECUTED` line. CI checks out the full history
  (`fetch-depth: 0`) and runs the red-phase tests in their own step, so the
  log shows them.

## Naming

- Module `c<id with _>` (`c004_27`), constant `SPEC`, function `run`,
  denial list `denials::DENIALS`.
- Test file `doc_<id>.rs`. Tests are named `ac<N>_<what the criterion
  says>` and `dod_<item>`; denials `ac<N>_denial_<what is broken>`;
  review-born denials `review_<finding>_<what>`.
- Criteria in the `Report` as the script printed them (`AC 1` becomes
  `AC1`, plus `DoD`, `WIRE`).
- Repo-state lines read `PASS <id> <criterion>: …` and `FAIL <id>
  <criterion>: …`.
