# 007a-11 — Invalid vectors per validity rule
**Epic:** 007a-Wire-vectors-and-harness · **Effort:** M · **Depends on:** 007a-05, 007a-06, 007a-07, 007a-08, 007a-09

## Context
- Deliverable: `vectors/wire/invalid/*.bin` + `*.json`, with, for every validity rule of the wire specification, at least one violating input and its required rejection reason `[decision]`. They are generated by `gen` (in the `hadronyche-tools` crate, C-133) from the machine-readable wire tables. The full list of validity rules and the rejection reason enumeration are an open sub-question of the epic owned by epic 004, which supplies the reject reasons (C-193).
- Rules from the epic and the constants table that must each have at least one violation `[decision]`:
  - wrong magic; version mismatch;
  - reserved fields non-zero in v1: copy index (2 bits, C-07); authentication scheme (8 bits) and tag (128 bits) of the authentication reservation (C-12, C-115);
  - wrong slice checksum;
  - inconsistent packet index / packet count;
  - UDP payload above 1 472 bytes on the default path; control message above 1 252 bytes of UDP payload (C-17), the path-MTU probe pair excepted (C-116);
  - a regime stamp section above 1 252 bytes (C-18);
  - more than 32 members per bundle, the controller member included (C-08, C-209), more than 256 streams per source (C-09);
  - truncated and over-long inputs for each message type.
- The 64-bit counter of the authentication reservation is **not** reserved: it is the live liveness counter (C-115). A non-zero counter is valid and must not appear as a reserved-field violation. Whether a non-advancing counter is a rejection is an open sub-question owned by epic 004; if the wire tables define such a rule, it is covered like any other rule.
- Required outcome for every invalid input: never crash, never change state, bounded time; drop and count per input and per reason `[decision]`.
- These vectors also seed the fuzz corpus (007a-15).

## Work
1. For each validity rule in the wire tables, have `gen` derive at least one violating input from a valid vector, with `.json` holding the `reason` from the rejection enumeration and the expected counter increment (1 for that reason).
2. Add truncation (every message type cut short) and over-length variants.
3. Add a path-MTU probe of 1 472 bytes as a negative control: it must not be rejected for exceeding C-17.
4. Commit the files to `vectors/wire/invalid/`.

## Acceptance criteria
1. Every validity rule in the wire tables maps to at least 1 invalid vector (list printed by a test).
2. Every rule listed in Context has at least 1 vector, including each of the 3 reserved fields (copy index, scheme, tag) separately.
3. No invalid vector has a non-zero liveness counter as its only violation.
4. Each invalid vector differs from a valid vector in a way that violates exactly one rule, stated in its `.json`.
5. All files carry `spec_version`, pass the 007a-02 schema test and are reproduced byte for byte by `gen`.

## Definition of done
- [ ] Tests green in CI, unprivileged
- [ ] Vector files carry the specification version they were generated from
- [ ] Every parser touched is fuzzed
- [ ] Every new factual claim carries an evidence tag
