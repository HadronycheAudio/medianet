# 027-14 — Handover scenario
**Epic:** 027-L3-cross-sink-rig · **Effort:** S · **Depends on:** 027-11, 027-22, 027-25, epic 004

## Context
- L3 rig: Linux host (clock holder, marker source, ALSA reference sink on capture channel 1), embedded device on channel 2, one capture clock; skew = ch2 − ch1 with inter-channel skew subtracted. Pass rule (C-79): p99.9 |skew| ≤ E_linux + E_device, max reported; E_linux target 50 µs (C-70).
- The rig has a second holder-eligible Linux host on the same switch as the new clock holder; C-212 makes it a required rig part (027-09).
- Rules: both sinks follow the same clock holder with the core servo: slew ≤ 10 ppm (C-60), rate change ≤ 1 ppm/s (C-61), lock bound ≤ 25 µs (C-62, pending simulation). Handover between holders is frequency-continuous; the L2 handover test uses a 50 ppm frequency difference (C-78), made up of the measured natural difference between the two holders' crystals plus an injected drift, both recorded in the run report (C-223). This scenario injects no drift: it records the measured natural difference only. Followers start an election after 1.5 s of reply silence (C-37). **Who may take over (settled, C-213):** a holder-eligible module whose time is usable — Locked, or in holdover with its alignment claim not lapsed (C-65, C-169); it takes over with frequency continuity and the timeline epoch is kept. Only when no candidate has usable time does the holder-eligible candidate with the lowest module id win and bump the timeline epoch (C-113) — that case is an epoch change, not a handover, and is not what this scenario tests.
- **Trigger (settled, C-212):** the handover is triggered as a holder loss: the old holder stops answering, each sink passes through about 2 s of holdover (C-37 plus C-33: 1.5 s of reply silence, then the 400 ms election window) and the new holder, the second Linux host, takes over. The holdover entry delay (C-195, pending simulation) is at or below C-37, so each sink is already in holdover with a growing bound when it calls the election. No on-demand handover control is needed. A run in which holdover was not observed is failed, not passed (C-212). **What L3 asserts (settled, C-220):** the skew between the two sinks stays within the sum of their E values (C-79, C-202) through holdover and takeover, and each sink's frequency is continuous at takeover — a rate change within C-61 (1 ppm per second) and no phase step (C-212). Per-sink emission error against the timeline is an L2 assertion only: the L3 rig cannot observe it, and this scenario neither asserts nor reports it (C-220). Frequency continuity is checked per sink on its own capture channel against the capture clock (027-25); a phase step common to both sinks would not show in the skew. The new holder has usable time (Locked) when the election runs, so it takes over with the epoch kept (C-213) and C-113 does not apply; an epoch change is a failure of this scenario.
- Clock state is read from the stamps (027-22); which fields carry it is the owned stamp-layout sub-question (epic 004), the values being published by the servo core through its time view (C-187).
- **027-AC-3, Handover:** across a holder change the skew stays within the limit and shows no step. "No step" uses `step_at` from 027-06 with the C-166 parameters: tolerance the larger of the two sinks' own no-step tolerances — ±1 sample (10.4 µs) for the Linux sink (C-166), the device's declared restart spread (C-191) — with both figures reported beside the verdict (C-203), comparison windows of 10 s, measured against the median of the first 60 s of the run. The handover is triggered 60 s into the run, and the 10 s comparison window starts when it completes, that is when the new holder has taken over (C-191, proposal pending first runs; C-212). This replaces the earlier provisional use of ±1 sample for the pair.

## Work
1. `RigControl::lose_holder()` — make the current holder stop answering sync requests mid-run (C-212) while the second Linux host stays holder-eligible and locked, so that it takes over by election; no other holder-eligible module with usable time is present, so the takeover is by that host (C-213); the rig method (stopping the holder module, or blocking its sync replies, without stopping the marker source or the Linux sink) is chosen here and documented in the rig procedure (027-09). There is no on-demand handover control (C-212 replaces the earlier `change_holder` by an epic-005 mechanism).
2. Scenario `handover`: run at least 10 minutes, holder lost 60 s into the run (C-191, C-212), so the baseline is the first 60 s; optionally hand back near the end the same way. Fetch both sinks' stamps at ≥ 1 Hz and log every multicast regime change through the handover (027-22); log the loss instant, each sink's entry into and exit from holdover, the takeover position, and check from the stamps that the timeline epoch did not change. If either sink's holdover is not observed, mark the run failed with that reason (C-212).
3. Read the device's declared restart spread from its stamp or declaration (epic 026) at the start of the run and compute the pair tolerance with `pair_tolerance_ns` (027-06, C-203). Report p99.9 |skew| over the whole run, and `step_at` from the handover's completion with the pair tolerance, windows and baseline used (C-166, C-191, C-203), and beside the verdict both sinks' own tolerances (C-203).
4. Per sink, call the takeover checks of 027-25 on the capture: rate change across the takeover against C-61 and phase at the takeover against the sink's own no-step tolerance (±1 sample for the Linux sink, C-166; the device's declared restart spread, C-191), and report them beside the skew verdicts (C-212).
5. Report the skew p99.9 and maximum within the interval from holdover entry to the end of the takeover against the limit (sum of the two sinks' target E values, C-79) as the C-220 assertion, with its verdict. The report carries no per-sink emission-error line: that is an L2 assertion only (C-220).
6. Note in the report the measured natural frequency difference between the two holders' crystals (no drift is injected here; the L2 test makes up its 50 ppm from this natural difference plus an injected drift, C-78, C-223), and the holdover duration seen by each sink.

## Acceptance criteria
1. **027-AC-3.** `p999_abs_ns <= limit_ns` over the whole handover run.
2. **027-AC-3.** The median of the 10 s window starting when the handover completes is within ± the pair tolerance — the larger of 10.4 µs (one sample at 96 kHz, the Linux sink's tolerance, C-166) and the device's declared restart spread (C-191) — of the median of the first 60 s (C-166, C-191, C-203); the report shows both sinks' tolerances beside the verdict.
3. The holder loss appears in the run log and the report, it lies 60 s after the run start (C-191), the takeover position is logged, and the timeline epoch is the same before and after (C-213).
4. **027-AC-3 (C-212).** Both sinks' stamps show holdover between the loss and the takeover; a run in which either sink's holdover was not observed is reported as failed, not passed. Skew samples within the holdover interval are included in the whole-run p99.9 of criterion 1.
5. **027-AC-3 (C-212).** For each sink, the rate change across the takeover measured by 027-25 is within C-61 (1 ppm per second), and its phase step at the takeover is within its own no-step tolerance (C-166, C-191); a run failing either is reported as failed with the sink and figure named.
6. **027-AC-3 (C-220).** The p99.9 and the maximum of |skew| over the interval from holdover entry to the end of the takeover are reported with a verdict against the sum of the two sinks' target E values (C-79); a p99.9 over that limit fails the run. The report has no per-sink emission-error line (C-220).
