# 026b — Reference device and porting guide

**Phase:** P6 · **Scope:** L (22 tickets, about 23 days) · **Depends on:** 026a, 007, 009, 012, 013, 014, 024, 024a, 025 · **Blocks:** 027

## Goal

Bring the runtime to a `no_std` microcontroller, second part: build one **reference device** — a narrow sink that joins a medianet as a follower — on a named board, on top of the hardware abstraction `hadronyche-embedded` and the host-verified device side delivered by 026a. The device runs the same `hadronyche-core` state machines and codecs as a hosted machine; it implements only transport, time and audio hardware. This part chooses the board, writes the firmware (network, time, identity, watchdog, audio output), answers the epic's measurement sub-questions on the board, runs the epic's acceptance tests on hardware, adds the remaining stamp fields (per-connection counters, alignment figures, alarms and peer DSCP, calibration factor, D and E values, restart spread), handles a change of A on the device, writes the porting guide and updates the design documents.

Epic 026 was split under C-143 (an epic above 40 days by ticket tally is split into lettered parts; a reference to epic 026 means both parts). Part 026a defines the traits and host mocks and integrates the device side with core on a host: identity, profile, poll loop and follower discovery, servo and holdover, admission, media path, rate actuator, audio edge, stamp publication, hosted collector and commissioning-window state. A narrow capture source on the same hardware is possible later behind the same traits, but it is not a deliverable of either part.

## Background

**Product frame.** Hadronyche Medianets are wired, isolated LANs whose only traffic is this runtime's. IP is **IPv4 only** in v1, multicast with TTL 1 (C-100). Modules exchange *slices* — all content of one stream for one stretch of media time — addressed by *position* on a domain-wide timeline: `position = (network_time − epoch_origin) × rate`; write `T(p)` for the network time of position p. The rate is the domain rate, 96 kHz, and it is the only rate on the wire (C-01). Linux hosts are the backbone (clock holder, elections, conformance, commissioning). macOS and Windows machines are edges. **Embedded devices are followers**: narrow sinks that never hold the clock in v1.

**The one implementation rule `[decision]`.** Control logic lives in `hadronyche-core` as pure state machines — discovery map, election, admission handshake, connection states: message and time in, messages and events out. A device **does not reimplement** hello, election or sync logic. It implements a **transport trait** (send and receive datagrams, join the discovery group, read time) and drives core. This is what makes one conformance suite (task 007) cover both profiles.

**What 026a provides.** The crate `hadronyche-embedded` (no_std, no alloc) with four board traits — `Transport`, `DeviceTime`, `AudioOut`, `Identity` — and the kit's `RateActuator` re-exported as the fifth (epic 024a, C-210, ratio range ±1 000 ppm); `Device<T, C, A, I>` with `poll() -> PollStats` (work done, elapsed time, running worst case), holding the kit's fixed 2:1 resampler node and the software-ratio adapter over the kit's steerable rate actuator (C-189, C-197); host mocks; the CI jobs and the no-alloc / no-libm symbol-check script; `profile.rs` (the embedded capability declaration) and `stamp_publish.rs` (sectioned publication); and the hosted stamp collector in `hadronyche-std`, whose record format and file names it documents (C-206). This part implements the four board traits on real hardware and builds no resampler.

Consequences already built into core:

- **Fixed-capacity peer map: 63 entries** (C-217): a medianet has at most 64 active modules, and commissioning refuses more (C-34); a module holds no entry for itself.
- **Control messages are binary and bounded:** at most 1 252 bytes of UDP payload (C-17), which is what the 1 280-byte IPv4 fallback path MTU leaves (C-06, C-100). The path-MTU probe pair is exempt: it is sent at the intended media packet size (C-116).
- Control messages carry the authentication reservation with scheme 0 and a zero tag; the 64-bit message counter is live because it is the liveness counter (C-115).
- The regime stamp is a **wire object**: a device cannot write files, so it **publishes its stamp over the network** and a hosted collector records it.

**Regime stamp transport (C-18).** The stamp travels in a dedicated control message split into sections that each fit C-17. It is multicast to the control group on any regime change and refreshed every 10 s; a unicast request gives an immediate fetch. The hello carries only a stamp version number. Capability fields take one of four states: present, absent, unverified, not requested (C-129). The device's stamp also carries:

- the receive-timestamp source, with one of the C-131 values (on a device: mac-hardware, interrupt, or userspace for a clock read after receive in the poll loop), in one of the four capability states;
- per-connection summary counters for every input: received, late, missing, marked gap, other-epoch, too-early, duplicates, incomplete reassemblies, demoted rounds, interrupted events, dead (C-159, completing C-47), plus the observed DSCP (C-47). Receiver reports are not multicast and there is no query message. A slice absent at its deadline counts missing and is reclassified late if it arrives later while its position is still within the ring span (C-108);
- per input, the lateness percentiles (50th, 99th, 99.9th and the maximum, C-160) and, in the alignment group, the reclaimable latency: offset − (current maximum lateness + headroom), when positive (C-157). Percentiles, reclaimable latency and the cannot-meet-A alarm use a rolling 60 s window, with the maximum since the connection went live reported beside them (C-182);
- the DSCP observed on each peer's hellos (C-152); the holder in turn reports the DSCP it observes on the device's sync requests, which is how the device's own marking is peer-verified;
- the calibration factor of the device target (time per abstract operation, C-106), measured once;
- the commissioning-window state: commissioning tools may drive test traffic only inside a declared window that every module stamps (C-107). The tool announces the window on the control group with an expiry time; modules stamp it while open; it closes at expiry or on explicit close (C-153). While a window is open, ordinary production measurements (latency, loss, alignment figures in stamps) are unqualified; the commissioning tool's own measurements (D, restart spread, certification) are valid commissioning results, each recorded with the window it was taken in (C-178). The window state itself is stamped by 026a (026a-13).

**Role `[decision]`.**

- **Follower only.** Holder eligibility is a capability bit in the hello; no v1 device sets it. Reasons: serving load (a holder answers 50 requests/s from each of up to 64 followers, C-35, C-36), availability (devices get power-cycled), oscillator quality. A device with MAC-level hardware timestamping can stamp *better* than a Linux host; "no kernel timestamps" is not the reason.
- After a holder loss, a holder-eligible module whose time is usable (Locked, or in holdover with its alignment claim not lapsed, C-65, C-169) takes over with frequency continuity and the timeline epoch is kept (C-213); a Locked candidate is preferred over one in holdover, and among equals the lowest module id wins (C-221). Only when no candidate has usable time does the holder-eligible candidate with the lowest module id win and bump the timeline epoch (C-113). A device is never a candidate, whatever its id. Seen from the device, a takeover with usable time is a change of holder with the epoch kept: its servo follows the new holder and its received streams are not restarted.
- Consequence to document for operators: a medianet needs at least one holder-capable (Linux) node, or there is no audio.

**Identity.** Module id 64 bits, instance nonce 64 bits, domain id 16 bits with 0 = unconfigured (C-11). A hello with domain 0 is ignored and counted by peers, not refused (C-173), so a device joins only once a non-zero domain id is stored on it. **Devices without a true random source must not draw the id from a pseudo-random generator** (forty devices would boot with the same id and the same nonce): mix a **hardware unique identifier with a persistent boot counter**. The module id is stable across reboots and the instance nonce changes on every boot: the nonce is what distinguishes successive instances of one module id, and third parties quarantine an id seen with two nonces until only one nonce has been seen for one hello-expiry period, 3 s (C-11, C-46, C-31). The derivation is 026a's (026a-03); the board supplies the hardware unique id, the persistent boot counter and the stored domain id.

**Clock.** The device runs the core follower servo against the holder at 50 sync requests/s (C-36), inside the accepted range of 10 to 200 per second (C-112). Requirements it inherits: published time continuous while locked; correction term at most 10 ppm from the holder's rate (C-60) and its rate of change at most 1 ppm/s (C-61) — these bound the servo's correction term, not the drift estimate it tracks (C-119); lock bound at most 25 µs (C-62, pending simulation); acquisition to Locked within 10 s (C-63, pending simulation); holdover bound grows 1 µs/s (C-64). Receive timestamps come from MAC hardware timestamping if the part has it, else from the receive interrupt; the source is a capability in the stamp (C-131). Wall-clock step detection lives in the platform backend that builds each exchange from receive stamps; on a device that backend is in `hadronyche-embedded`, and the servo only receives exchanges that passed it (C-121). The device enters holdover after the holdover entry delay, which is pending simulation (epic 008b proposes it) and expected at or below the 1.5 s election silence threshold, so the device is already in holdover with a growing bound when the election on 1.5 s of reply silence starts (C-195, C-37). The clock lock state and bound are published by the servo core (epic 008a) through the published time view (C-187); the device reads them and computes none of its own.

**Holdover margin.** The alignment claim lapses when the holdover bound exceeds the module's E; from the lock bound this takes (E − C-62) / C-64, about 25 s for the Linux reference sink's 50 µs (C-65, C-70). For the device the margin is its own declared E (C-73). A device that declares E unknown takes as its fixed reference twice the lock bound (2 × C-62, that is 50 µs) and stops claiming alignment when the bound it currently publishes exceeds that value, about 25 s into holdover at the growth of C-64 (C-169). When the claim lapses the clock state is Unlocked with time unusable: one-way figures and alignment claims stop (C-162). A commissioned device stays commissioned while its clock is unlocked: its declared E is kept, its alignment claim is suspended and does not count towards a group's required E until the clock is locked again, then resumes without re-commissioning (C-180).

**Audio edge.** Same contract as every edge: `emit(p) = T(p) + A`, `submit(p) = emit(p) − D`, where A is the presentation group's audition offset (C-55) and D the device's declared plumbing delay. Two-loop timebase from core (built in task 018, wired into `Device` by 026a-10): loop 1 device clock → domain line; loop 2 device sample counter → device clock, by regression over (sample count, timer-captured time) pairs — on a device, a timer capture of the audio DMA position.

- **v1 device clock is 48 kHz.** The wire stays at 96 kHz; the edge converts 2:1 through the kit's resampler node (C-80, C-01); 2:1 is one of the two ratios for which the node is offered, because its delay is a whole number of samples (C-105). A resampler node may appear only inside an edge module, and the edge's conversion delay is part of its plumbing delay D (C-134), never of L; the manifest reports the conversion delay separately, on the device-facing port (C-207): D is the total delay from hand-off to emission, driver buffer, resampler and converter included (C-170). The **rate actuator** is a separate resampler (C-189): the kit's DSL resampler node is fixed-ratio (2:1 or 1:2, whole-sample delay, C-105), while the rate actuator is steerable, its ratio varying by parts per million around its nominal value to track the device's crystal; its delay is also part of D. **Both resamplers come from the arithmetic kit (epic 024a)**, which builds them once; every edge, the device included, uses the kit's and builds none of its own (C-197).
- **Rate-actuator trait with one v1 implementation: software ratio**, an adapter over the kit's steerable rate actuator (C-197). The `RateActuator` trait is defined by the kit epic (024a) together with its implementation, with a ratio range of ±1 000 ppm around the nominal ratio; every edge consumes it (C-210). `hadronyche-embedded` defines four traits and re-exports the kit's `RateActuator` as the fifth of a device's hardware surface; `Device` holds the software-ratio actuator internally, which is why it is generic over four traits. Hardware clock trimming can be added later behind the same trait with nothing on the wire.
- **E** for a device is declared per device (no fixed platform target) with the common definition: the 99.9th percentile of absolute emission error over a one-hour certification run, the maximum reported beside it (C-73). The device also declares its own restart spread of D, measured at L3 (C-191). Only the commissioned certification state gives a numeric E; until a commissioned run is done the device declares E as unknown (C-140); it is then refused with reason RequiredEExceeded by any presentation group that sets a required E and admitted to groups that set none (C-103). Cross-sink skew is judged against the sum of the two sinks' E values (C-79, task 027). Paired with a different sink, the no-step and recovery tolerance is the larger of the two sinks' own, with both sinks' figures reported beside each verdict (C-203); the device's side is stated against its declared restart spread.

**Capacity.** A stream is one packet per slice by default: 48 frames = 0.5 ms (C-02), 6 channels (C-04), 4-byte samples (C-03): 192 bytes per channel per slice, 1 152 bytes of audio, no per-channel id byte — the channel map is in the manifest (C-04). About 1 320 bytes on the wire (C-20), 2 000 packets/s, about 21.1 Mbit/s (C-21). A 100 Mbit device port holds about **19 channels** at the 70 % admission ceiling (C-26, C-23). A device is a narrow sink: it subscribes only to the bundle members (streams) it needs. The unit of subscription is the stream, so the device receives and buffers all 6 channels of a subscribed stream and selects the channels it plays through the manifest's channel map; a 2-output codec plays 2 of them. Alignment rings are sized to the presentation group's A (C-96) and hold wire slices at the domain rate, so buffer memory is channels × 4 bytes × 96 000 × A: 23 040 bytes for one 6-channel stream at A = 10 ms. Admission checks this **buffer memory** and refuses beyond the device's declared limit. A commissioned change of the device's A reaches it through the commissioning tool, inside a declared commissioning window: the tool validates buffer memory first and then announces the new A to the group's members (C-224, C-153, C-211). A change of A while the stream is live re-enters aligning with the ring and ratchet ceiling resized, as the sinks do (C-186); the device switches at its own position, one lead (C-43) ahead, with nobody to announce it to (C-214); the receiver report carries the device's current A (C-198). The commissioning tool checks the declared buffer memory of every consumer that buffers to meet A, the device included, before applying a change of A and refuses one that does not fit (C-211, C-222); if one reaches the device anyway, it keeps the deepest ring its declared memory holds as its ceiling, raises the cannot-meet-A alarm (C-174) and keeps its stream running (C-211, C-222); the alarm stays raised until a later change of A that fits, and the receiver report carries the A the device was given, not the clamped value (C-216). The reference device subscribes to audio members only; were a device to subscribe to a controller member, admission (epic 012) would cost it by C-219. Since the port holds about 19 channels, a 7th channel (a second stream) can only be refused on the declared memory limit, not on the port.

**Liveness (unchanged).** Interrupted after 8 consecutive missed slices, 4 ms (C-38); only slices absent at the deadline count as misses — a marked gap or a slice on another timeline epoch proves the upstream is alive and resets the count (C-102). Dead after 2 s (C-39), counted from the last slice received with content or a marked gap (C-111); a slice on another timeline epoch also restarts the dead clock and has its own counter (C-135). These describe streams the device receives: a sink-only device's own liveness, as seen by its producers, is judged by the producer timeout (C-41, C-168). Receiver report per bundle every 100 ms (C-40); the producer stops after 2 s without reports (C-41). In-band announcements: lead 64 slices (C-43), re-issued every 16 (C-44). A Pending connection whose target is absent persists until the target appears or the operator cancels (C-45). Persistent lateness (a late slice in each of 10 consecutive 1 s windows, C-101) triggers a ratchet step of one slice period (C-53); at the ceiling A the input is Demoted (C-109). A ratchet step is a re-alignment like any other: an upstream fan-in takes it at a position it announces one lead (C-43) ahead in its own output (C-215), which the device sees as an in-band announcement on the input it consumes; the device, a sink with no output, takes its own step at its own position one lead ahead (C-225), as for a changed A (C-214). An aligned multi-packet input uses the consumer's own deadline for reassembly (C-110). The drain per input is bounded to 2 × its admitted packets per slice in each slice period (C-16, C-156). A connection alarm is raised on refusal, interrupted, dead, demoted, cannot-meet-A and control-degraded (C-173); cannot-meet-A is maximum lateness + D + headroom above A in each of 10 consecutive 1 s windows (C-174). The session number of each stream is assigned by its source (C-19).

**What weakens on `no_std` `[decision]`.**

| Guarantee on hosted | On the device |
|---|---|
| Housekeeping isolated from the data plane; no shared lock | Not enforced by an OS. The implementer must show **bounded control handling**; otherwise stamped *report-only*. The control-isolation capability is absent or unverified unless that bound is shown (C-161) |
| Supervised, restartable housekeeping | **Unsatisfiable.** Any fault is a whole-device reset (watchdog) |
| Privilege report (real-time scheduling, memory lock) | Replaced by a profile declaration: *embedded, by construction*. Strict mode is hosted-only; a device stamps real-time scheduling and memory lock as present by construction (C-147) |
| Fault injection, interface drop counters, DSCP marking | Each may be **absent**; stamped with the C-129 states. A test-only fault hook, including the panic-injection hook (C-145), is stamped like any injection (C-120) |
| Record and replay of exact-class modules | Done on a host: the same generated `no_std` code is rerun against captured input |
| Multi-packet slices, skew buffers | Bounded by declared memory; admission refuses beyond it |
| Files | None; the stamp is published on the network (C-18) |

**Module code on the device.** Generated by the DSL compiler (task 024): one `no_std` process function, no allocation, state and stack sizes as constants, kit arithmetic only. Its cost bound is counted in abstract operations per slice, identical on every machine; admission converts it with the target's calibration factor (C-106), measured by the DSL conformance suite (epic 025) running a reference workload once per listed target (C-176). Exactness between host and device is promised only for the **exact-fixed** class.

**Where outputs live.** Measurement results and bench logs go to `doc/design/reports/`, specifications to `doc/design/spec/` (C-130). Host-side harnesses and tool binaries (traffic generators, the stamp-collector command line, bench controllers) go in the `hadronyche-tools` crate; throwaway probes in `probes/` (C-133). Datasheet figures carry `[memory]` until checked; a figure cited from a published standard carries `[standard]` with its clause (C-132). Reference hardware is proposed by the implementing team, approved by the product owner and recorded in the constants table (C-172).

## Acceptance criteria

These are the epic criteria of epic 026, completed on the reference device; their ids are kept. Their host-verifiable share is met first in 026a (026a-AC-1 to 026a-AC-9).

1. **026-AC-1 (AC-35).** The device joins as a follower with a **63-entry peer map** (C-217); control handling is bounded (worst-case `poll` time measured and stated) or stamped *report-only*; its stamp is **published over the network** (C-18) and recorded by the hosted collector.
2. **026-AC-2 Memory fit.** Static memory for the 63-entry peer map (C-217), one 6-channel stream with A = 10 ms (23 040 bytes of ring at the domain rate, C-96), the servo, the resampler node and the rate actuator (C-189) fits the reference device with at least 25 % headroom; the figure is recorded.
3. **026-AC-3 Follower only.** The hello never carries the holder-eligible bit, even when the device has the lowest module id (C-113). With the Linux holder removed, the device goes to holdover, its bound grows at 1 µs/s, and it stops claiming presentation alignment once the bound exceeds its declared E (C-65); it stays commissioned and resumes the claim after relock without re-commissioning (C-180). When a second holder-eligible node with usable time takes over, the epoch is kept and the device's stream is not restarted (C-213, C-221).
4. **026-AC-4 Identity.** With the true-random source disabled, two devices flashed with identical firmware boot with different ids and nonces; rebooting one keeps its id and changes its nonce. A device with domain id 0 is ignored and counted by peers (C-173).
5. **026-AC-5 Conformance.** The device passes the protocol conformance vectors of task 007 over its real Ethernet interface (hello, admission, sync, media, receiver reports).
6. **026-AC-6 Exactness.** An exact-fixed DSL module produces on the device the same output hashes as on the host, by replay of captured input.
7. **026-AC-7 Liveness.** Pulling the cable: the producer stops after 2 s without reports (C-41); on reconnect within 2 s of the last slice (C-111) the stream resumes at the frozen offset; after 2 s it is re-admitted.
8. **026-AC-8 Fault = reset.** An injected control-path fault (C-145) resets the device; its producer judges it gone by the producer timeout, stopping 2 s after the last receiver report (C-41, C-168: interrupted and dead describe received streams, and the reference device sends none); it rejoins with the same module id and a new nonce.
9. **026-AC-9 Admission refusal.** A request for a 7th channel (a second stream, beyond the device's declared buffer memory) is refused with a named reason.
10. **026-AC-10 Edge figures declared.** The device's D (with method, C-170), its own restart spread of D (measured at L3, C-191) and E (C-73 from a commissioned run, or unknown per C-103 and C-140) are in its stamp; contributes to AC-29 (cross-sink skew, verified in task 027).
11. **026-AC-11** No allocator and no libm symbol in the firmware image.
12. **026-AC-12 Stamp content.** The stamp recorded by the collector carries the capability fields in the C-129 states (real-time scheduling and memory lock present, C-147; control isolation per C-161), the receive-timestamp source (C-131), per-connection summary counters for the device's input (C-47, C-159), lateness percentiles (C-160) and reclaimable latency (C-157), the DSCP observed on each peer's hellos (C-152), the commissioning-window state (C-107, C-153), and the target's calibration factor (C-106, C-176).
