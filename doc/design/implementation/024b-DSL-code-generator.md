# 024b — DSL code generator

**Phase:** P5 · **Scope:** L (21 tickets, about 32 days) · **Depends on:** 024a, 004, 009, 010, 013, 015, 023 · **Blocks:** 025, 026

Epic 024 is split into two parts by rule C-143: part 024a delivers the runtime ABI and the arithmetic kit; this part (024b) delivers the DSL code generator, which compiles against both. A reference to "epic 024" means both parts.

## Goal

Build the back half of the DSL compiler: the **code generator** in `hadronyche-dsl` that turns checked IR (epic 023) into one `no_std` pure-Rust process function implementing the `Module` trait of part 024a, with its constants, gap defaults, join padding, degraded marking, an operation-counting build, and, for exact-float modules, a determinism fingerprint evaluated on the processing thread; and the `hadronyche-dsl build` command that writes the module, its manifest and its vectors file. Compile-time rejections (among them controller placement, the bundle cap and the even-tap FIR) are implemented by the front end (epic 023); this part only asserts that it never receives such a program (C-218).

## Background

**Product frame.** Hadronyche Medianets are wired, isolated LANs whose only traffic is this runtime's. Modules exchange *slices* — all content of one stream for one stretch of media time — addressed by *position* on a domain-wide timeline (`position = (network_time − epoch_origin) × rate`, where rate is the domain rate, 96 kHz, C-01). Linux hosts are the backbone; macOS and Windows machines are edges; embedded devices are followers. The same generated code must run on a hosted machine and on a `no_std` device.

**Boundary.** The runtime owns *when and whether*: it stamps positions, aligns inputs, fires deadlines, classifies gaps; on hosted platforms the hosted backend (epic 015) emits the gap slice when a module misses its own deadline and raises the processing-overrun event (C-144). Module code owns *what*: the content of the outputs for position p given the inputs at position p.

**What part 024a provides.** The ABI in `hadronyche-core::abi`: `ABI_VERSION = 1`; `ModuleInfo { abi_version, state_bytes, stack_bytes, cost_ops_per_slice, determinism, inputs, outputs (each with latency: Latency, a whole number of domain-rate samples, and the "frequency-dependent delay" property, which the ABI keeps for recursive filters, C-189), fingerprint }`; `InputSlice` (with `gap`), `OutputSlice` (with `degraded`); the `Module` trait (`INFO`, `State`, `init`, `process`); `check_module_info`; `Fingerprint`, `fingerprint_matches` and `effective_class`. The kit `hadronyche-kit`: Q1.31 / Q0.32 fixed point with `mul_high`; strict f32 helpers and `sine`; shipped checksummed tables; linear ramps; the 2:1 / 1:2 resampler node with `group_delay` as a whole-sample `Latency`. The tools `check-symbols`, the aborting test allocator and `gen-tables` in `hadronyche-tools`. Three CI targets (x86-64, AArch64, one 32-bit device target), recorded as the listed-target set for exact-float, with a shared result-vector runner.

**Rules for generated code `[decision]`.**

- **One process function:** `process(state, inputs at position p with per-input gap flags, position) -> outputs`.
- **Never blocks. No allocation at process time.** State size and worst-case stack are compile-time constants emitted with the code. Devices need static memory. `stack_bytes` is produced by this code generator from the compiled artefact, because only the compiled code shows the real stack; the method is chosen in ticket 024b-16.
- **No libm, no transcendental functions.** Only the kit (part 024a).
- **Float operations are never reordered**; no fused multiply-add contraction; summation order is defined by DSL semantics. No auto-vectorisation that changes results.
- **Position invariant.** Output for position p is derived from inputs at p. The module cannot set positions. If the module has structural latency L, the *runtime* stamps the output p − L; generated code simply produces the delayed content and exposes L as a constant. L is always a whole number of domain-rate samples, in the manifest and in the ABI (C-105).
- **Resampler node and edge modules.** The DSL resampler node is fixed-ratio, offered only at 2:1 and 1:2, whose delay is a whole number of samples; other ratios are out of v1 (C-105, C-189). It may appear only inside an edge module; the compiler rejects it anywhere else (C-134); the front end (epic 023) implements that rejection and this generator only asserts it never receives such a program (C-218). An edge's conversion delay is part of its plumbing delay D (driver buffer, resampler and converter, C-170), not of any output's L (C-134): an edge's resampler delay is counted only in D and never in L, L being the module's structural delay in the domain-rate timeline, and the manifest reports the conversion delay separately, on the device-facing port (C-207). The wire carries the domain rate only (C-01); an edge whose hardware runs at 48 kHz converts 2:1 (C-80). An edge's rate actuator is a separate, steerable resampler whose ratio varies by parts per million around its nominal value to track the hardware crystal; it is not a DSL node, this generator does not emit it, and its delay is part of D (C-189).
- **Joins.** Where DSL paths of different latency meet at a join, the compiler pads the shorter path with a whole-sample delay line, reports the inserted delay in the manifest, and the module's L is the longest path; an explicit DSL construct opts out per join. A path with frequency-dependent delay is padded on its structural part only and the join is flagged in the manifest (C-104). On the device side of an edge module, paths that differ by an odd number of domain-rate samples cannot be padded with a whole-sample delay line at the device rate; the compiler rejects such a join and suggests the per-join opt-out (C-190); the front end implements that rejection and this generator only asserts it never receives such a join (C-218). Each output whose path has frequency-dependent delay (recursive filters) carries the ABI's "frequency-dependent delay" property (C-189). An even-tap linear-phase FIR is rejected by the compiler in v1, with a diagnostic suggesting an odd-tap design, so that L stays exact (C-183); the front end implements the rejection and this generator only asserts it never receives such a program (C-218).
- **Gap defaults** generated per content type: audio zero-fill; dense controllers hold last value, and each dense controller declares an initial value in the manifest (default 0), used when a gap precedes any received value (C-158); sparse keyed controllers rely on state refresh — a sparse ramp runs over one slice and ends at its target, so after a gapped slice the sparse state is the state reached at the end of the previous slice; read-only transport state holds the last known state with the playhead advanced as that state dictates — a stopped transport stays where it is, a playing one moves on at its tempo — and the output is marked degraded (C-141); a stopped playhead does not advance through a gap (C-200); before any transport state has arrived, a transport input reads stopped, playhead at zero, tempo 120 beats per minute (C-184, C-199). DSL constructs may override.
- **Degraded marking per output from dataflow:** the degraded flag follows the content (C-122): an output at position p is degraded if and only if an input it depends on was flagged gap at p − L, where L is that output's latency. Generated code therefore keeps the gap flags of the last L samples of each relevant input in its state; when L is not a whole number of slices, the output is degraded if any input slice contributing to it was gapped. For L = 0 this is "an input flagged gap in this slice".
- **Determinism class** is carried as a constant: exact-fixed (bit-exact everywhere), exact-float (bit-exact only where the fingerprint matches), bounded. The bounded class arises only from an exact-float fingerprint mismatch and for hand-written (non-DSL) modules that do not claim exactness; the DSL has no non-deterministic node in v1, so the code generator never declares a module bounded (C-123).
- **Fingerprint.** For exact-float modules the generator emits a compile-time input vector and expected output bits, covering subnormal and NaN-producing paths. The runtime evaluates it at start **on the processing thread itself**, because floating-point modes are per thread and audio stacks change them. Match ⇒ exact-float eligible; mismatch ⇒ the module runs as bounded-class and the regime stamp says so. Vector layout: words are laid out by input port in `INFO.inputs` order, 48 frames per slice, channel-interleaved 4-byte samples, as many slices as the vector holds; the state is a fresh one from `init`; an exact-float module without a fingerprint is not exact-float eligible.
- **Cost bound.** `cost_ops_per_slice` counts abstract operations per slice and is identical on every machine. Each target has a calibration factor (time per operation), measured once and recorded in the regime stamp; admission converts with it (C-106). The conformance suite (epic 025) measures the factor by running a reference workload once per listed target (C-176).
- **Content domains v1:** audio; dense controllers; sparse keyed controllers (one field of one voice moving linearly to a value over the slice); read-only transport state. No transport authoring.
- **Where controllers travel.** A bundle source's controllers always ride in their own member stream (C-181, C-205), and that controller member counts towards the 32 members of C-08: a source with controllers has at most 31 audio members (186 channels), and a wider source with controllers is rejected at compile time (C-209). A single-stream source may always put its controllers in a second stream, and must do so when headers plus controllers exceed the 100-byte cap (C-137); it may share the audio packet while they fit (C-181, permissive). The compiler checks this from the manifest (C-181); the front end (epic 023) implements the rejections, and this part's build command, which writes the manifest, records the placement and only asserts that it never receives a program that breaks these rules (C-218, ticket 024b-12).

**Constants.** Slice 48 frames = 0.5 ms at 96 kHz (C-01, C-02); 96 kHz is the only rate on the wire. Samples are 4 bytes, f32 or Q1.31 (C-03). A stream carries 6 channels at defaults: 192 bytes per channel per slice, 1 152 bytes of audio per slice, no per-channel id byte; the channel map is in the manifest (C-04). Wide ports are bundles of up to 32 members, the controller member included (C-08, C-209). Edge hardware at 48 kHz converts 2:1 through the kit's resampler node (C-80). The machine pair for cross-machine bit-exactness is x86-64 and 64-bit ARM (C-151).

**Regime stamp.** The regime stamp is a dedicated control message, split into sections that each fit one packet at the fallback MTU, multicast on any regime change and refreshed every 10 s (C-18). Epic 013 defines the message and its field layout; the hosted backend (epic 015) sends it (C-144). This part sets the per-module effective determinism class through it.

**Where outputs live.** Specifications go in `doc/design/spec/`, reports and measurement results in `doc/design/reports/`, the constants table is `doc/design/02-constants.md` (C-130); the architecture specification is `doc/design/01-architecture.md` (C-171). Throwaway probes go in `probes/`; harness and tool binaries go in the `hadronyche-tools` crate (C-133). Nothing is written into the frozen POC tree.

**Fuzzing.** Each parser is fuzzed 60 s on every change and 1 hour nightly; the corpus is kept (C-95).

**Evidence tags.** `[code]`, `[measured]`, `[kernel-doc]`, `[memory]`, `[decision]`, and `[standard]` for a figure cited from a named, published standard with its clause (C-132), for example IEEE 754 behaviour.

**Test corpus.** Criteria that speak of "programs" use one shared corpus of DSL programs, defined in ticket 024b-04 and reused by later tickets: a gain, a mix of two inputs, a ramped sparse controller, a fixed-point sine oscillator, a decaying feedback structure, an edge module with a 2:1 resampler, and a program with a padded join. Each has an exact-fixed variant and, where it uses floats, an exact-float variant; the two variants count as one program (C-192). The mix's volume is the reference dense controller (C-192).

**Cross-platform float exactness (why exact-float is scoped).** Results can differ through: fused multiply-add contraction; non-IEEE handling of subnormals (flush-to-zero or denormals-are-zero modes, set per thread); NaN payloads; 80-bit intermediate precision on legacy x86 targets. The generator avoids the first by construction; the fingerprint detects the others at run time. Exactness between a host and a small device is promised only for exact-fixed.

## Deliverables

**Crate `hadronyche-dsl`, module `codegen/`:**

- `emit.rs` — IR → Rust source implementing `Module`, with `INFO` filled from the manifest; lowering of IR operations to kit calls.
- Latency computation — each output's L as the longest path in whole domain-rate samples (C-104, C-105); the edge conversion delay recorded for the manifest on the device-facing port as a component of D, never added to L (C-134, C-207); an assertion that no resampler outside an edge module or at another ratio reaches the generator (C-105, C-134, C-218).
- `gaps.rs` — default concealment (including dense initial values, C-158, and transport hold with playhead advance for a playing transport and none for a stopped one, C-141, C-200, and the before-first-state transport, C-184, C-199) and overrides.
- `joins.rs` — whole-sample padding delay lines at joins, the inserted delays and frequency-dependent-join flags reported in the manifest (C-104); an assertion that no device-side join of an edge module whose paths differ by an odd number of domain-rate samples reaches the generator without the opt-out, the front end having rejected it (C-190, C-218).
- The "frequency-dependent delay" property set on each output whose path has frequency-dependent delay (C-189).
- `degraded.rs` — per-output flag from dependency sets, delayed by the output's latency (C-122).
- `fingerprint.rs` — vector synthesis for exact-float modules.
- An assertion that no even-tap linear-phase FIR reaches the generator, the front end having rejected it (C-183, C-218).
- An operation-counting build of a generated module, used to check `cost_ops_per_slice` (C-106).
- Controller placement recorded in the manifest as the front end decided it, with an assertion that no program breaking the placement rules or the bundle cap reaches the build command: a bundle source's controllers in their own member stream, counted towards the 32 members; a single-stream source's controllers in the audio packet only within the 100-byte cap, a second stream always allowed (C-137, C-181, C-205, C-209, C-218).
- A command `hadronyche-dsl build <source> --out <dir>` producing the Rust module, the manifest (binary and readable) and a vectors file, with fuzzed decoders for the binary manifest and the vectors file. Every generated module is of an exact class (C-123), so every build writes a vectors file.
- Runtime-side evaluation of the fingerprint on the processing thread, setting the effective determinism class in the regime stamp.

## Dependencies

- **Needs:** the ABI, kit, tools and CI targets of part 024a (all of it); the runtime's slice delivery shape and gap flags (009); content message layouts, the ABI auxiliary types and bundle demultiplexing (010); the regime stamp message and the field that carries a module's effective determinism class (013, C-144); the hosted backend that sends the stamp (015, C-144); checked IR, analyses (including dependency sets and which nodes have frequency-dependent delay), the cost analysis, the manifest schema and the DSL constructs for gap overrides, join opt-out and edge modules (023); the wire header sizes that count against the 100-byte cap (004, C-137).
- **Provides:** generated modules, manifests and vectors files to the conformance suite (025) and to the embedded device (026).
- **Between the parts:** this part depends on 024a as a whole; 024a depends on nothing here.

## Acceptance criteria

1. **024b/AC-1 No allocation, no libm.** Generated modules build `no_std` without `alloc`; symbol inspection of the built artefact shows no libm symbol and no allocator symbol. Running under an allocator that aborts on use passes.
2. **024b/AC-2 Bounded stack.** Measured stack use at process time never exceeds `stack_bytes` on the hosted target and on one device target.
3. **024b/AC-3 Contributes to AC-32.** exact-fixed programs are bit-identical on every listed target; exact-float programs are bit-identical where the fingerprint matches; a forced mismatch (flush-to-zero enabled on the processing thread) makes the module run bounded-class and sets the stamp field. No generated module declares the bounded class (C-123).
4. **024b/AC-4 Fingerprint placement.** The fingerprint is evaluated on the processing thread; a test that changes the floating-point mode on that thread only (not the main thread) is detected.
5. **024b/AC-5 Gap defaults.** With an input flagged gap: audio input reads as zeros; a dense controller reads its last value, or its declared initial value if no value was received yet (C-158); sparse state is unchanged; a transport input reads the last known state with the playhead advanced as that state dictates (a playing one moves on at its tempo, a stopped one does not advance), and dependent outputs are degraded (C-141, C-200); a transport input gapped before any state has arrived reads stopped, playhead at zero, tempo 120 beats per minute (C-184, C-199). An override declared in the DSL replaces the default.
6. **024b/AC-6 Degraded marking.** For a program where output A depends on input 1 only and output B on inputs 1 and 2: a gap on input 2 marks B degraded and not A. For an output with latency L, the flag is set on the output that carries the content of the gapped input (position p − L), not on the output produced in the same call (C-122).
7. **024b/AC-7 Cost bound.** A generated 6-channel gain module's counted operations per 48-frame slice are identical on every CI target and do not exceed `cost_ops_per_slice`; its measured processing time on the CI machine does not exceed `cost_ops_per_slice` times that machine's calibration factor (C-106, C-176).
8. **024b/AC-8 Join padding.** A program in which two paths of different latency meet at a join has the shorter path padded with a whole-sample delay line so that both arrive aligned; the manifest reports the inserted delay; the output's L is the longest path; with the opt-out construct on that join, no padding is inserted; a path with frequency-dependent delay is padded on its structural part only and the join is flagged in the manifest (C-104), and that output carries the "frequency-dependent delay" property (C-189); a join on the device side of an edge module whose paths differ by an odd number of domain-rate samples compiles with the opt-out and is padded at the device rate when the difference is even (C-190); the generator asserts it never receives such an odd-difference join without the opt-out, the front end rejecting it (C-218).
9. **024b/AC-9 Output latency.** Each output's L is a whole number of domain-rate samples equal to the probe-measured delay of the generated module (contributes to AC-33: compiler L equals the probe-measured value). An edge module's conversion delay is reported as a component of D, separately on the device-facing port, and is not part of any L (C-134, C-207); the code generator asserts that it never receives an IR with a resampler outside an edge module or at a ratio other than 2:1 and 1:2 (C-105, C-134), or with an even-tap linear-phase FIR (C-183); those programs are rejected by the front end (epic 023) and tested by the conformance corpus (epic 025a) (C-218).
10. **024b/AC-10 Controller placement.** The manifest records each source's controller placement as the front end decided it: a bundle source with controllers and 31 audio members (186 channels) builds with its controllers in their own member stream; a single-stream source's controllers may share the audio packet while headers plus controllers fit the 100-byte cap, or ride in a second stream at any size (C-137, C-181, C-205, C-209). The build command asserts that it never receives a bundle source with controllers and 32 audio members, or a single-stream source sharing the audio packet beyond the cap; the front end (epic 023) rejects those and the conformance corpus (epic 025a) tests it (C-218).
