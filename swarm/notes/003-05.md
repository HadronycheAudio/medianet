## Answer to the lock sub-question (for 003-08 and 003-10)

*"Does deadline pacing change the servo's lock behaviour enough to alter the baseline?"* — No, in the direction that matters `[measured]`: in both runs the clock reached LOCKED at ≈4.1 s (≈2.1 s after the election), inside the 25 s smoke run with a wide margin, and the achieved rates (49.86 and 944.77 exchanges/s) supersede the pre-fix baseline figures (38 and 75) for BASELINE.md. The falsifier (lock is no longer reached within the 25 s smoke run) did not fire, so there is nothing to escalate to the design owner before 003-09. Caveat for 003-08/003-10: the headless per-second line's `clock LOCKED ...` field is not by itself evidence of the follower lock in this topology — the aggregator watches the sender module (`main.rs` start loopback), and here the sender won the election, so from ≈2 s that line echoes the holder's own trivially-LOCKED view (module.rs:1501, the holder writes state LOCKED, err 0 into its sync view). The lock evidence above is the followers' `lock` column in the metrics CSV (their real servo state) and the map lines' per-module `clock` fields; 003-02's headless-line caveat applies the same way.

## Method — 003-02's method with the duration correction

Exactly the method recorded in 003-02 (`swarm/notes/003-02.md`), with the divisor re-derived from the run and the duration correction from `swarm/status.md` / the 003-04 check: rate = sum(served over intact holder windows after the dropped first window) ÷ covered span (from the rows' own unix-ms stamps) ÷ follower count (from the run's `map:` lines and the follower rows with `asked > 0`), not the literal mean-served/3 (which reads ~2.5-3.4 % high because a metrics row covers ~1.02 s of housekeeping, not 1 s — measured intervals here: ~1015 ms at the slow rate, ~1026 ms at the fast one). No code change, no added instrumentation, no packet capture; the counting uses the POC's own `served`/`asked` take-and-reset counters written once per `HELLO_NS` window (module.rs:50, module.rs:1370) by the 003-03 process-owned writer (`src/metrics.rs`), so the CSV is now one clean row per module per window — the 003-02 interleaving grammar still accepts every row and discards none of these files, and the field positions of `served`/`asked` are unchanged (header `METRICS`, module.rs:1277).

Run validity — 003-02's rules applied unchanged, both runs pass:

- **Clean-run precondition.** Both logs: exactly one join per module (3 `joined from` lines + the local sender), a `map: 4 modules` line, and one election (`election 1`, one `clock: sender holds it`). No duplicate-module flake.
- **Degenerate-file rule.** 23 intact holder windows per run; the first is dropped, 22 are averaged — far above the ≥ 2 minimum.
- **Chimera guard.** With a pacing allowance: at the slow rate, 11 kept holder windows carry served = 153 or 156, above the inherited literal bound 150 (followers × configured rate). These are legitimate deadline-paced windows — the row covers ~1.02 s (~51 slots) and the deadline loop answers one catch-up exchange after a late window — so the guard is applied as followers × rate × 1.05 (157 at the slow rate, 3150 at the fast one), under which zero rows are rejected; the largest observed counts (served 156 / asked 1006) are nowhere near chimera-fragment magnitude (003-02's chimera example was asked = 1794655331577). Recorded here so 003-08 inherits the adapted bound knowingly.
