## Results

- `--sync-hz 1000`: **75 exchanges/s** per follower (75.7 in run 1, 74.7 in run 2) `[measured]` at `poc-untouched`.

Both figures are comparable to P-02 (37 and 77 `[measured]`): within about 3 %, in line with the M-1 explanation — one effective receive timeout of about 13 ms paces the exchange loop, so 1000/13 ≈ 77 exchanges/s at the fast rate, and two such timeouts per 20 ms period give about 38 exchanges/s at the slow rate. The mechanism cited in M-1 is code-confirmed: the clock thread blocks in a receive with a 5 ms timeout after every send and again after every reply (`clock_sock.set_read_timeout(Some(Duration::from_millis(5)))`, module.rs:1126; loop at module.rs:1504-1600).

## Method — how completed exchanges are counted, without modifying the POC

The measurement uses only existing output of the frozen POC `hadropoc`; there is no code change, no added instrumentation and no packet capture (capture tools were considered and rejected: tcpdump is not installed and `/usr/bin/dumpcap` is mode 0750 root:root, unusable unprivileged). The POC already counts completed clock exchanges itself: the clock holder answers every request and accumulates the counter `served`, and every follower accumulates `asked` once per reply received (module.rs:1572-1580), one reply completing one exchange. The housekeeping thread writes both as take-and-reset counters into the metrics CSV — one row per module per second, because the write interval is `HELLO_NS = 1 s` (columns in module.rs:1292; interval in module.rs:50; take-and-reset at module.rs:1426-1428). The counting step is: run `loopback` with `--metrics` pointed at a file outside the POC tree, then parse that CSV and read the `served` field of intact rows of the clock holder — a row whose `name` field equals its `holder` field and whose `holding` field is 1. Each such row covers exactly one 1 s metrics window, so its `served` value is the number of completed exchanges in that second, summed over the 3 followers. The achieved rate per follower is the mean of `served` over the intact holder windows, dropping the first intact window (it can cover a partial second around the clock election), divided by 3. As a cross-check the `asked` field of intact follower rows gives the rate seen from the follower side: 34-40 exchanges/s at the slow rate and 69-79 at the fast one, agreeing with the holder-derived figure within a few percent. Caveat `[code]`: in `loopback` all four modules open the same single `--metrics` path, each truncating it at startup (module.rs:1354; known defect bug 1), so the file holds interleaved row fragments; a row is counted only if all 39 comma-separated fields parse as intact (the grammar is fully specified under "Reproducibility" below), which filters the garbled fragments out.

### Reproducibility (5 % claim)

A second engineer reproduces a figure by running one command per rate (below, about 25 s each), then applying this grammar to the metrics file `[measured]`:

1. Split the file on newlines, split each line on commas into tokens.
2. A token position `j` starts an accepted row when: token `j` is one of the four module names `sender`, `synth1`, `synth2`, `mixer`; token `j+1` is one of those names (the holder); token `j+2` (holding) and `j+3` (forced) are each 0 or 1; token `j+4` (servo state) is a small integer; tokens `j+25`, `j+26` (turnaround mean/max) and `j+28`, `j+29` (rtt mean/min) match `<digits>.<digit>`; tokens `j+27` (served) and `j+30` (asked) and `j+31..j+34` (datagrams, connections, band, points) are plain integers. Everything else — fragments produced by the interleaving of bug 1 — fails this test and is discarded.
3. Take the rows where holding = 1 (the holder), discard the first, average their `served` values, divide by 3.

Run-to-run spread was 2.4 % at the slow rate (38.4 vs 37.5) and 1.3 % at the fast rate (75.7 vs 74.7), and intact windows inside one run spread about ±3 % around their mean, so the 5 % reproduction bound holds `[measured]`. The parser used here is exactly the grammar above (kept at `/tmp/opencode/003-02/parse.py` with the raw metrics files `metrics-50.csv`, `metrics-50-r2.csv`, `metrics-1000.csv`, `metrics-1000-r2.csv`); rewriting it from the grammar takes minutes and needs no POC knowledge beyond module.rs:1292.

Arithmetic, in full:

- Run 1, `--sync-hz 50`: intact holder windows served = 112, 118, 115, 112, 113, 120, 116 (first intact window, 110, dropped); mean = 115.1; 115.1 / 3 followers = 38.4 exchanges/s.
- Run 2, `--sync-hz 50`: intact holder windows served = 113, 108, 106, 118, 118 (first, 115, dropped); mean = 112.6; 112.6 / 3 = 37.5 exchanges/s. Reported figure: 38 exchanges/s.
- Run 1, `--sync-hz 1000`: intact holder windows served = 230, 228, 219, 229, 226, 233, 231, 225, 223 (first, 236, dropped); mean = 227.1; 227.1 / 3 = 75.7 exchanges/s.
- Run 2, `--sync-hz 1000`: intact holder windows served = 226, 222 (first, 229, dropped); mean = 224.0; 224.0 / 3 = 74.7 exchanges/s. Reported figure: 75 exchanges/s.
